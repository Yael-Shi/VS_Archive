# VS-Archive AI Context

VS-Archive is a Django backend project for managing historical family documents.

## Main domain

- **`ArchiveItem`** is the long-term central archival content entity. The product archive is **`/archive/`** (unified list/detail direction), not separate mini-sites per item type.
- **`OCR_DOCUMENT`:** **`Document`** remains runtime source of truth for OCR/processing fields. For the six shared archival fields, **`ArchiveItem`** is canonical on create (`create_ocr_document`), staff OCR metadata edit (`/archive/manage/<id>/edit/`), and user-facing display; **`Document`** holds compatibility mirrors. **`Document`**-centric list/review paths remain for OCR operations (`/api/ui/documents/`, `/api/ui/admin/review/`). Primary OCR create/upload UI is **`/archive/manage/new/?item_type=ocr_document`** using **`/api/uploads/*`**; **`/api/ui/upload/`** remains a fallback. Do not assume sync from Django Admin **`Document`** edits. See **`docs/ai-context/ocr-archiveitem-cutover.md`**.
- **`MANUAL_TEXT`:** **`ArchiveItem`** + **`ManualTextContent`** are runtime source of truth. Staff/admin create via **`/archive/manage/new/`** (manual-text branch; legacy alias **`/archive/manage/new/manual-text/`**) and edit via **`/archive/manage/<id>/edit/`**. No **`Document`**, no OCR/HTR, no SQS. Body is **not** in **`DocumentTextResult`**.
- **`ArchiveItem.visibility`** is the access-control source of truth for all **`ArchiveItem`** types (`public` / `private`). **`private`** means private family archive content (visible to authenticated **`archive_family`** group members and staff/admin), not staff-only content. Helpers in **`archive_item_access.py`**. **`Document.visibility`** remains a temporary bridge field; OCR document list/detail access uses **`document.archive_item.visibility`**. Family invitation/account-management is deferred.
- **Public `/archive/` search/filter:** full-text ``q`` remains authoritative for ranking. Structured advanced filters (`author` as one **`Author.id`**, repeatable `category`/`event`/`tag`/`person` ids, `year`/`year_to` overlap) compose on the same authorized queryset via ``archive_advanced_search.py``. Repeatable ``person=<person_id>`` is ArchiveItemPerson **or** identified renderable PhotoPerson (OR within Person, AND across groups); ``people_present`` does not match. List results remain one ArchiveItem; PHOTO cards may deep-link to ``?photo=`` and use that photo’s thumbnail when a single renderable PhotoContent truthfully represents the selected Person set (one selected Person: earliest matching PhotoPerson appearance, including AIP+PP overlap; several selected People: only a photo containing **all** selected ids; otherwise the ordinary item URL/primary thumbnail). Active Person filter chips are **one per selected Person id**: canonical name → ``archive-person-detail``; visible × removes only that id (preserves other filters/`q`/`item_type`/`per_page`, drops `page`, always keeps ``advanced=1``). Other chips stay grouped. PR2 adds the public advanced-search panel (`advanced=1`), active-filter chips, server-side reverse/malformed year validation, and conditional choice-context loading (not on every ordinary/q-only request; Person and Author choices follow the same rule). **PR3 completes the planned search chain** with a compact shared-nav header form (`partials/nav.html`) that submits q-only GET to ``archive-list`` (fresh `/archive/?q=…`; no advanced/current query state carried; nav input stays empty by default). No second search backend/view. Advanced search remains on `/archive/`. Public ``q`` author text and snippet match-source ``נמצא במחבר/ת`` use ordered **`ArchiveItemAuthor`** names when any structured links exist, else trimmed **`author_name`**. The advanced **author** filter is single-select **`Author.id`** via **`ArchiveItemAuthor`** (legacy **`author_name`** only for zero-link items when that **`Author.name`** is globally unique **and** the Author already has structured membership in the authorized queryset being filtered). Deploy of this Author ``q`` cutover **requires** **`backfill_archive_search_index`** before the new metadata contract is live (stale structured-item **`author_name`** tokens must stop matching; structured **`Author.name`** tokens must match). Broader ideas (Hebrew morphology, fuzzy OCR / pg_trgm, phrase search, places authority, `related`) remain separate future work.
- **`PHOTO`:** **`ArchiveItem`** is the umbrella record; a PHOTO item may own **1..N** **`PhotoContent`** rows (FK `related_name="photo_contents"`). Staff create via **`/archive/manage/new/?item_type=photo`**. Staff can add/edit/reorder/delete individual photos on the PHOTO manage page; a PHOTO item must keep at least one `PhotoContent`. ## Current implementation (OCR/HTR)

**Gemini** is the **production/default** engine for all routed pairs except Hebrew handwritten. Static `OCR_ROUTES` in `documents/services/ocr_routing.py` remain Gemini-only for the pairs that still use Gemini.

**Transkribus** is **implemented** (Legacy TrpServer / PyLaia), but **not** broad production-default:

- Real adapter + engine: `TranskribusAdapter`, `transkribus_engine.py`.
- Worker routing: `language=he` + `HANDWRITTEN` requires Transkribus. `ENABLE_TRANSKRIBUS_HEBREW_HANDWRITTEN=true` activates that route; if the flag is off, routing fails fast instead of using Gemini.
- Existing `TRANSKRIBUS_DEV_UPLOAD_MODE`, `TRANSKRIBUS_USE_EXISTING_SERVER_DOCUMENT`, `TRANSKRIBUS_FORCE_REPROCESS`, and `TRANSKRIBUS_RECOGNITION_ONLY_RETRY` remain execution/recovery controls, not route-selection flags.
- Manual smoke: `python manage.py dev_transkribus_transcribe <file> --confirm-create-transkribus-doc`.

**Not implemented:** Gemini→Transkribus fallback, Transkribus→Gemini fallback, hybrid OCR routing, broader Transkribus routing beyond Hebrew handwritten, product/admin reprocess workflow, cleanup automation, general re-OCR on successful Trp runs, remote Trp deletion, or automatic paragraph inheritance.

**Durable `PROCESS_DOCUMENT` rollout:** Request model, typed worker outcomes, request-aware worker fencing, and the generic enqueue service are implemented. Successful single-file `upload_complete` and multi-image `upload_finalize` now use `enqueue_uploaded_document_processing` with `origin=UPLOAD_FINALIZE`; repeated completion coalesces against active history and treats matching terminal upload history as idempotent. Document-state updates are fenced by Request status, and expected enqueue failures use safe typed responses. When a `RUNNING` Request lease expires, the Request is fenced to `RECOVERY_REQUIRED` and a related Document still at `PROCESSING` is set to `Document.processing_state_user=RECOVERY_REQUIRED` in the same transaction (staff label **נדרש טיפול בעיבוד**). That overlay is not engine-scoped DTR rollup, is not automatically replayed, and does not authorize a new provider call. An already-running retained matching-token holder may finish persistence while the Request is `RUNNING` or `RECOVERY_REQUIRED`; terminal, mismatched, or cleared tokens skip automated SOURCE/HEBREW persist, search-index replacement, and stale-runtime rollup. The Request may terminalize only after the Document is `READY` / `PARTIAL` / `FAILED`. Staff abandon of a parked Request is implemented as a service (`abandon_process_document_request`): `RECOVERY_REQUIRED → FAILED` with `failure_code=STAFF_ABANDONED` and overlay replacement to an ordinary result state. Staff document detail exposes that service as a POST-only action when a `ProcessDocumentRequest` is `RECOVERY_REQUIRED` (including when the Document overlay is already READY/PARTIAL/FAILED). The action does not enqueue or retry. Intentional-retry orchestration is not implemented yet. The ECS task role has explicit SQS send permission. Worker `receive_message` VisibilityTimeout is 45 minutes (2700s), matching the durable execution lease and post-claim visibility refresh; competing live-lease defer remains 120s. `ApproximateReceiveCount` is logged for observability only. Production callers — upload/finalize (`process_document_upload_enqueue`), OCR reprocess (`process_document_ocr_reprocess_enqueue`), and Hebrew translation retry (`process_document_hebrew_translation_retry_enqueue`) — enqueue through `enqueue_process_document_request` and `send_process_document_request_message(request_id)`. Legacy `send_process_document_message(...)` and worker `{type, document_id}` PROCESS_DOCUMENT execution remain only for mixed-version / in-flight compatibility; that compatibility applies only when both `request_id` and `lease_token` keys are absent (present-but-malformed identity is fail-closed). No production caller in this repository was found. CDK-configured jobs-queue `maxReceiveCount` is **100** (SQS delivery/handler safety net, not a provider retry budget). Live AWS was verified **100** after the 2026-09-07 `vs-archive-dev-data-v2` deploy. The existing jobs DLQ remains attached (source retention 4 days, DLQ retention 14 days, CDK default visibility 10 minutes). Automatic DLQ redrive is unimplemented and forbidden. `RECOVERY_REQUIRED` is not automatically replayed and DLQ is not authorization for provider replay. DB-side expired `RUNNING` `ProcessDocumentRequest` fencing is implemented and deployed: operators can fence without SQS redelivery via `fence_expired_process_document_requests` (dry-run default; scoped `--apply`; same Document-then-Request transition as worker claim; no provider/SQS). `recover_process_document_requests` remains the separate stranded `QUEUED` / `ENQUEUE_FAILED` resend tool and does not replay `RUNNING` or `RECOVERY_REQUIRED`. Corrected/current sync is out of scope for the expired-lease fence command; corrected/current DB-side STARTED fencing remains deferred. Heartbeat, automatic DLQ redrive, and queue split remain deferred.

**Corrected/current staff sync queue (PR1 schema + PR2 worker + PR3 enqueue service + staff fetch UI):** durable **`TranskribusCorrectedCurrentSyncRequest`** per document enqueue intent; top-level SQS type **`SYNC_TRANSKRIBUS_CORRECTED_CURRENT`** handled by the existing worker (claim/reclaim, 45m lease + visibility, 2m defer, atomic Request↔Attempt link before provider I/O, idempotent terminal reconciliation). Linked stale **`STARTED`** (≥60m) → **`RECOVERY_REQUIRED`** (keeps **`lease_token`**, clears **`lease_expires_at`**; no provider rerun; late fenced worker may still terminalize). Guarantee: at-most-once provider orchestration per Request, not exactly-once delivery. **PR3** adds `enqueue_transkribus_corrected_current_sync` (Document-lock send-right; post-send CAS; no `QUEUED`/`RUNNING`/`RECOVERY_REQUIRED` resend; stranded pre-send `QUEUED` deferred to recovery/requeue). **Staff UI POST** on the existing corrected/current attempts page enqueues via that service only (no sync in the web process; no automatic activation). Feature gate / recovery command remain deferred. Management command **`sync_transkribus_corrected_current`** unchanged (no Request correlation).

**Recognition-only retry V1 (dev/staging):** when `TRANSKRIBUS_RECOGNITION_ONLY_RETRY=true`, dev upload mode may re-run PyLaia on an existing Trp `remote_doc_id` without a new upload — **recovery only** (failed/incomplete upload-created attempts). Excludes `SUCCEEDED` source runs; blocks if any `DocumentTextResult` is `VERIFIED`. `TRANSKRIBUS_FORCE_REPROCESS=true` still means a new upload/new Trp document. See `decision-log.md`.

**TranskribusRun persistence:** Transkribus adapter paths persist one row per attempt (remote ids, job ids, attempt status). Worker passes generic `document_id` only.

**Cleanup / retention V1:** `python manage.py report_transkribus_cleanup` is a dry-run local reporting command. It classifies `TranskribusRun` rows and grouped `remote_doc_id` lineages for operator review, but it does not call Transkribus, delete remote docs, or delete local rows.

**Duplicate upload guard (PR3):** dev upload mode blocks a second Trp upload for the same `(document_id, UPLOAD_CREATED, collection_id, model_id)` when a prior blocking run exists. Override with `TRANSKRIBUS_FORCE_REPROCESS=true` (new Trp doc) or recovery with `TRANSKRIBUS_RECOGNITION_ONLY_RETRY=true` when a reusable source run exists. See `decision-log.md`.

**Transkribus paragraph presentation (PR1 metadata + PR2 public rendering + PR3 staff editor/status):** v1 is Transkribus-only. Staff-authored paragraph boundaries are presentation metadata on a `TranskribusTranscriptSnapshot` (`TranskribusParagraphMapping` + `TranskribusParagraphBreak` after contributing source lines). They do **not** modify `DocumentTextResult.text`, snapshot canonical text, snapshot lines, geometry, char offsets, hover IDs, or search offsets. A mapping row with zero breaks is an explicit one-paragraph save; no mapping row means grouping was never saved. New snapshots do not inherit mappings; historical mappings remain stored. Currentness follows binding structural freshness + same snapshot (not `hover_eligible`). **Public rendering (PR2):** when `assess_paragraph_mapping_currentness` reports a current mapping, the public document detail transcription is wrapped as human `<p>` groups over existing hover/search fragments (A-style overlay). No/stale/other-snapshot/drifted mappings keep the legacy renderer unchanged. Canonical separators (`\n`, `\n\n`) stay in the DOM; CSS collapses them visually inside a paragraph while source-line spans keep `pre-wrap`. A page boundary is not a paragraph boundary. Gemini, manual text, photo, and video paths are unchanged. **Staff editor/status (PR3):** authorized staff edit paragraph breaks on `ui/admin/documents/<id>/transkribus-paragraphs/` against the current displayed/bound Transkribus snapshot, in original source-line order (not flowed prose). Save uses `save_paragraph_mapping` (POST/PRG, CSRF, `_require_admin_page` + `get_viewable_document`). Zero-break save is an explicit one-paragraph mapping. A stale-submit token (`expected_document_id`, `expected_text_result_id`, `expected_snapshot_id`) refuses writes if the bound snapshot or structural freshness changed. Status appears on the Transkribus versions page (“תעתוק Transkribus המוצג כעת”) and as a compact staff-only note on document detail; it reflects the current snapshot only. **Historical suggestion/adoption (PR4):** when the editor’s current bound snapshot is structurally fresh and has no mapping, eligible older mappings may be offered as optional suggestions (PR1 correspondence proof). Multiple eligible sources are listed newest-first for explicit staff choice; none is auto-adopted. Adoption is a dedicated POST (`.../transkribus-paragraphs/adopt/`) that creates a new current mapping with `copied_from` and refuses if a current mapping already exists. Versions/detail do not run historical discovery or show adopt actions. Cross-snapshot transfer remains a fail-closed `(page_index, provider_line_id)` identity proof.

## Routing layer (done)

Engine selection is implemented as a small routing layer (`select_ocr_route` → `transcribe_pages` → adapters), not as logic inside views or a provider-specific worker.

## OCR review lifecycle (current)

**Automatic OCR/HTR success** (`run_worker._save_htr_results`):

- **`DocumentTextResult.status=NEEDS_REVIEW`** (Gemini, Transkribus, and any worker success path)
- **`verification_status=UNVERIFIED`**
- **`NEEDS_REVIEW`** = usable/displayable text that still needs human review; **not** a technical failure
- **`FAILED`** = pipeline/dispatch/routing failures only
- **Write-time VERIFIED fence:** if any `DocumentTextResult` for the document is **`VERIFIED`** at successful automated persist time, skip creating/updating automated SOURCE/HEBREW rows and do not replace the search-index body with that late result. Restore the pre-run `processing_state_user` (do not roll up from the unused runtime engine or from one VERIFIED row’s engine). `REJECTED` does not fence. Ordinary `UNVERIFIED` reruns and cross-engine writes remain allowed when no row is `VERIFIED`.

**Human ground truth:** **`verification_status=VERIFIED`** is the human-approved layer. Row **`status`** does not replace that.

**Public text quality:** persisted **`DocumentTextResult.quality`** is **`UNKNOWN`/`LOW`/`MEDIUM`/`GOOD`** (default **`UNKNOWN`**; no historical inference). Effective public quality: **`VERIFIED` → `HUMAN_VERIFIED`**, **`REJECTED` → `NEEDS_CORRECTION`**, else the persisted base value (`documents.services.text_quality`). **`HUMAN_VERIFIED` and `NEEDS_CORRECTION` are not stored.** Automatic **LOW/MEDIUM/GOOD** is currently scored only for **Arabic printed banded SOURCE_TEXT** from completed `page_quality` values plus assembled text (missing/blank assembled text stays **UNKNOWN**; `[UNCLEAR]` caps all-UNASSISTED **GOOD** to **MEDIUM**; ≥ half `CLOUD_VISION_LOW_QUALITY` is **LOW**; `ASSISTED`/`MIXED` alone are **MEDIUM**). Gemini, Transkribus, non-banded Antigravity, and other OCR routes remain **UNKNOWN**. The worker writes SOURCE_TEXT `quality` only when `HtrResult` explicitly supplies a persisted value. Successful Gemini Hebrew translations of non-Hebrew OCR persist **`HEBREW_TEXT.quality`** as the inherited same-engine SOURCE_TEXT base quality (`capped_inherited_base_quality`; no independent translation score; verification_status is not used). Missing SOURCE fails closed to **UNKNOWN**. Hebrew-native / Transkribus **`HEBREW_TEXT`** is unchanged (OCR mirror; does not copy `HtrResult.quality`). Failed translations do not inherit. No historical backfill. Staff **`MANUAL_TEXT`** is **`HUMAN_VERIFIED`** in that helper only. Public OCR detail shows **one** quality indicator on the **displayed transcription** (`text_quality_presentation`): SOURCE_TEXT for non-Hebrew documents; for Hebrew-language documents, the existing single-panel transcription choice (HEBREW_TEXT preferred, else SOURCE_TEXT). The translation panel has **no** separate public badge. The tooltip’s translation-dependency sentence appears **only when a Hebrew translation is displayed alongside transcription**. `MANUAL_TEXT` detail uses the same shared indicator without that sentence; it is rendered in the top metadata/status area, not inside the manual text body. OCR document-detail placement remains `document-detail-top-meta`. Public OCR `פרטים טכניים` no longer shows auto-OCR or “human-reviewed” notes; the control is omitted for public `READY` and keeps only the processing wait copy for public `PROCESSING`. Staff technical-details content is unchanged. `/api/ui/documents/` stays publicly reachable for visibility-allowed items, but staff processing/upload status badges (**מוכן לצפייה** / **חלקי** / **עיבוד נכשל** and related) render only for staff/admin. `/api/documents/` is the OCR **document-list** JSON (not the public `/archive/` catalog API). Non-staff item objects contain only `id`, `title`, `date_start`, `date_end`, `language`, `doc_type` (`title`/`date_*` from `ArchiveItem`; archival dates, not `Document.created_at`/`updated_at`). Staff/admin still receive `text_input_type`, Document timestamps, legacy `category_event`, `Document.tags_m2m` `tags`, `processing_state_user`, `upload_status`, `metadata_status`, `visibility`, `admin_meta`, and file fields. `?upload_status=` and `?metadata_status=` filtering, and the HTML upload-status and metadata-status filters/chips/column, are staff-only. Non-staff remain gated to `Document.upload_status=UPLOADED`. `ArchiveItem.metadata_status` is staff/editorial catalog-completion (`NEEDS_COMPLETION` / `COMPLETED`); it does **not** change public membership or visibility. Public `/archive/` does not show it to non-staff. Engine-marker identity is unchanged.

**Parent document rollup:**

- **`READY`** = all expected outputs exist and are usable/displayable (non-empty text; `SUCCEEDED` or `NEEDS_REVIEW`). **Not** human-verified.
- A document may be **`READY`** while results are **`NEEDS_REVIEW`** + **`UNVERIFIED`**.
- **`PARTIAL`** = missing, incomplete, failed, or unusable expected outputs — **not** merely review pending.
- **`NEEDS_REVIEW` alone does not force `PARTIAL`** when expected usable rows exist.

**Review reasons:** policy token **`AUTOMATIC_OCR_REQUIRES_HUMAN_REVIEW`** on every automatic success; **`NEEDS_REVIEW_FLAG`** only when **`HtrResult.needs_review=True`**; plus **`MIN_TEXT_LENGTH`**, **`HAS_UNCLEAR`**, and engine-provided reasons.

**`SUCCEEDED`** remains valid in the schema for future trusted paths; current automatic worker persistence normally uses **`NEEDS_REVIEW`**.

## Hebrew result types (current behavior)

For Hebrew documents, the worker persists **both** `SOURCE_TEXT` and `HEBREW_TEXT`; processing-state rollup for **`READY`** requires **`HEBREW_TEXT` only** (usable per rollup rules above). See `decision-log.md` and `.cursor/rules/architecture.mdc`.

## Non-Hebrew `PARTIAL`

Non-Hebrew documents may remain **`PARTIAL`** when **`HEBREW_TEXT`** is missing or translation failed — **intentional**, not an OCR failure. **`READY`** rollup requires usable **`SOURCE_TEXT`** and **`HEBREW_TEXT`**.
